# AI 场景重建后回归测试计划

## 1. 测试目的

本轮测试用于确认 AI 重建模型、调整场景或重写脚本后，原有 VR 消防逃生功能是否仍然正常，并验证本轮新增或修复的功能。

本文件夹中的记录必须来自真实检查或真实测试。不得根据代码推测填写“通过”，也不得把 AI 生成的测试结论当作人工实测结果。

## 3. 统一工作流程

1. 1号在修改前记录基准提交，并对 AI 生成或修改的内容进行人工审核。
2. 2—5号按照各自文档执行专项测试，发现问题后建立 GitHub Issue。
3. Issue 必须包含测试版本、复现步骤、预期结果、实际结果和证据。
4. 1号按 Issue 修复，每个问题尽量使用独立、小范围提交，并在 Issue 中填写修复提交编号。
5. 原问题负责人拉取修复版本，重新执行相同测试并记录复测结果。
6. 专项测试通过后，6号从主菜单到结算界面执行完整回归。
7. 只有真实执行过的测试才允许标记为“通过”。未在 VR 设备上测试的项目必须标记为“未实机测试”。

## 4. 测试状态

每条用例只能使用以下状态之一：

- `未测试`：尚未执行。
- `通过`：实际结果与预期结果一致，并已记录测试版本。
- `失败`：可以复现问题，应填写 Issue 或问题编号。
- `阻塞`：由于设备、场景、前置功能或构建失败而无法测试。
- `不适用`：当前版本明确不包含该功能，并写明原因。

## 7. 证据要求

- 截图或视频应能看出测试对象及结果，不只拍摄静态画面。
- Console 报错应保存完整的首条错误及调用栈。
- 每次测试必须绑定具体 commit SHA。
- 修复前与修复后尽量使用相同操作路径录制，便于对比。
- 如果使用 AI 协助分析或修改，应记录 AI 的作用以及人工审核、调整和验证内容。

## 8. 通过条件

本轮回归完成需同时满足：

- 2—5号负责的阻断级和严重级用例全部通过；
- 暂停菜单可以恢复游戏；
- 结束界面按钮可以操作；
- 未正确使用湿毛巾时，进入烟雾区会按设计扣血；
- 教学完成后可以离开教室；
- 到达指定避难终点后显示总结反馈；
- 轮椅同学支线能够触发，并在流程或总结中得到反馈；
- 6号完成至少一次指定版本的完整流程回归；
- 所有遗留问题均已记录，不得以删除失败记录的方式视为通过。
